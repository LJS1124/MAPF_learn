5.1任务陆续到达：一条改派链

第 2 章把整张价格表一次涨完。真实的派车窗口里，任务是陆续到达的：已经按最优派好了前 k 个任务，第 k + 1 个到了，最优派法要怎么变？

本章沿用第 2 章的场景：6 辆车（V6 是备用车）、5 个任务，代价矩阵不变，最优总时间 124 s。任务按 T1 到 T5 的顺序到达。前四个到达时不需要想什么：每个任务拿走当时最便宜的空闲车。T1 拿 V3（6 s），T2 拿 V5（23 s），T3 拿 V2（32 s），T4 拿 V4（9 s）。这四次到达，最优派法都没有动过已经派好的任务。

T5 到达时情况变了。它离 V5 最近（10 s），可 V5 正在做 T2。此刻空闲的车只有 V1 和 V6，去 T5 分别要 82 s 和 74 s。

读图

前四个任务，贪心和最优没有区别。每次到达，最便宜的空闲车正好就是最优的选择，改派链只有一个环节：新任务拿走一辆空闲车。

第五个任务，最优要动两个已经派好的任务。最优做法不是去找空闲的车，而是让 V5 转去做 T5，T2 改派给 V2（多 38 s），T3 再改派给 V1（多 6 s）。三个改动加起来的净增量是 54 s，比“不改派”的 74 s 少 20 s：被改派的 T2、T3 都变贵了（合计 +44 s），但 T5 从 74 s 降到 10 s，省下 64 s。

边际成本随顺序变，总和不变。默认顺序下五次到达的边际成本是 6、23、32、9、54，合计 124。换一个顺序，各步的边际成本会不同，最后的总和仍然是 124：每一步之后的派法，都是“当时已到达任务”上的最优。

贪心是长度为 1 的改派链“拿最便宜的空闲车”只允许一种改动：新任务直接占一辆空闲车。匈牙利算法允许沿任意长的链改派，并且在所有链里挑最便宜的一条。下一节说这条链怎么找。

5.2一次插入的内部：约化成本上的最短路

找最便宜的改派链，是一个最短路问题。边的长度是第 2 章的约化成本，路径从新任务出发，到任意一辆空闲车结束。

先把记号对齐。任务价格 uj（可正可负），车价格 vi ≥ 0，约化成本 rij = cij + vi − uj ≥ 0，r = 0 的边是紧边。算法一直维持三件事：所有约化成本非负；已配对的边都是紧的；空闲的车价格为 0。第 2 章的证书检查器说的正是这三条，所以只要它们在，当前派法就是最优的。

新任务 j0 到达。要给它找车，可以直接选一辆车 i1。如果 i1 正被任务 j1 占着，j1 就得搬家，选一辆新车 i2，依此类推，直到碰到一辆空闲车。这是一条交替路：任务 → 车 → 车原来的任务 → 车……每一步“任务选车”的代价是这条边的约化成本，“车推出原来的任务”不花代价（那条边是紧的）。所以：

边际成本u0 + Du0 = mini(ci,j₀ + vi)，直接选最便宜车的成本；D = 交替路上约化成本之和的最小值，是改派多付的部分

T5 的例子：u0 = 10（V5 的 10 s，此时 V5 的车价是 0），D = 44，边际成本 54。“不改派”的做法是在空闲的车里挑，相当于只允许长度 1 的路径，多付 64 s。

求最短路用 Dijkstra。标签 di 是“从新任务出发，到达车 i 的最短距离”，等价于第 2 章里“要把新任务的价格再涨多少，车 i 才会变成紧边”。完整的一次插入分六步：

  1. 标价。uj₀ = mini(ci,j₀ + vi)。此后所有 ri,j₀ ≥ 0，至少一个为 0。
  2. 初始标签。di = ri,j₀，前驱 predi = j0。
  3. 扫描。在还没扫描的车里取 d 最小的 i*（并列取编号小的）。标记它已扫描。
  4. 停止或展开。若 i* 是空闲车，停止。否则设 j′ 是它当前的任务：j′ 也要搬家，对每辆未扫描的车 i，若 di* + ri,j′ < di，就更新 di 和 predi = j′，然后回到第 3 步。
  5. 涨价。记 D = di*。每辆已扫描的车（终点除外）vi += D − di，它当前的任务 u 涨同样多；新任务 uj₀ += D。
  6. 翻转。从 i* 沿 pred 回溯，任务逐个改派，得到改派链。

为什么这一步之后，价格仍然是公道的

涨价的规则看起来只是一组加减，要确认它没有把任何约化成本推成负数。三类边分开看：

  • 配对的边（车和它的任务）。车 v 涨了 D − d，任务 u 涨同样多，r = c + v − u 不变，仍是 0。
  • 路径上的新边。Dijkstra 保证沿最短路每条边的“d 差”恰好等于它的约化成本，涨价之后这条边的约化成本变成 0。改派翻转以后，它们成为新的配对，正好是紧的。
  • 其他边（一端在树里，另一端不在）。树里的任务涨了 D − d（它的车被扫描时的标签），松弛保证 di ≤ d + r（i 是未扫描的车，r 是这条边原来的约化成本），而 Dijkstra 又保证未扫描的车 di ≥ D，所以 r ≥ D − d：这条边只减少 D − d，不会变负。

终点车的增量是 D − D = 0，所以空闲的车价格仍是 0。三条不变量都保持住，第 2 章的互补松弛成立，当前派法对已到达的任务是最优的。同时可以看出：新任务的最终价格 uj₀ 就是这次到达的边际成本。其他配对的任务和车成对涨价，一个加一个减，对 ∑u − ∑v 没有贡献，多出来的只有 uj₀ = u0 + D。

和第 2 章的图 2-6 是同一件事那里每一次“给被争抢的车涨价 δ”，在这里是 Dijkstra 的一次扫描：δ 的累计就是标签 d。第 2 章的涨价拍卖把许多次小涨价一步步做完；这里把它们合并成一次最短路，涨价一次到位。两者停在同一张价格表上，最终价格与 HiGHS 报告的一致。

5.3写成代码：O(n³) 是怎么来的

上面六步写成 Python，大约三十行。Lab 练习 2 就是让你写这一段，并让它通过第 2 章的证书检查。

def insert(self, j0):                                  # 新任务 j0 到达    C, u, v, m = self.C, self.u, self.v, self.m    u[j0] = min(C[i][j0] + v[i] for i in range(m))     # 1 标价：最便宜的 成本 + 车价    d = [C[i][j0] + v[i] - u[j0] for i in range(m)]  # 2 标签 = 约化成本    pred = [j0] * m                                     #   前驱：谁“够到”了这辆车    scanned, order = [False] * m, []    while True:                                         # 3 Dijkstra：数组版，O(m) 取最小        i_star = min((i for i in range(m) if not scanned[i]), key=lambda i: (d[i], i))        scanned[i_star] = True        order.append((i_star, d[i_star]))        jp = self.task_of[i_star]        if jp is None:                                  # 4 碰到空闲车：停            break        for i in range(m):                             #   否则 jp 也搬家：松弛，O(m)            if not scanned[i]:                cand = d[i_star] + C[i][jp] + v[i] - u[jp]                if cand < d[i]:                    d[i], pred[i] = cand, jp    D = d[i_star]    for i, di in order[:-1]:                         # 5 涨价：扫描过的车和它们的任务一起涨        v[i] += D - di        u[self.task_of[i]] += D - di    u[j0] += D    i = i_star                                          # 6 沿前驱翻转：改派链    while True:        j = pred[i]        prev = self.vehicle_of[j]        self.vehicle_of[j], self.task_of[i] = i, j        if j == j0:            break        i = prev

复杂度

每辆车在一次插入里最多被扫描一次，所以第 3 步最多执行 m 次；每次扫描做一遍第 4 步的松弛，是 m 次比较。一次插入 O(m2)，n 个任务共 O(n m2)，方阵就是 O(n3)。这里用数组而不是堆存标签：图是稠密的，每次扫描本来就要看全部 m 个标签，堆省不下什么。

O(n3) 是最坏情况，平时远没有这么糟。下面的实验数的是“扫描了多少辆车”和“松弛了多少次”，它们不依赖机器，每次跑都一样。

随机矩阵上，每次插入只扫描一小部分车。价格把车分开了，新任务很快就碰到一辆空闲车，n = 320 时平均每次十几辆，总松弛次数增长得比 n3 慢。乘积矩阵上，第 k 次插入扫描 k 辆车，总数 n(n+1)/2，每次扫描又要松弛 n 次，三次方增长一目了然。Lab 练习 2 的测试里就有这一条。

手写 Python 版比 SciPy 慢两个数量级左右，差距来自解释器，不是算法。真正的差距在右边两列：把同一个指派问题当成 LP 或 MIP 交给 HiGHS，比 SciPy 慢两到四个数量级，规模越大差得越多。第 2 章的结论在这里再确认一遍：识别出这是指派问题，比会调求解器重要得多。

窗口重算，还是增量维护？每个窗口有几百个任务的时候，从头解一次就是几毫秒，比维护增量状态更不容易出错，也更容易测试。增量的价值有两处：任务流非常密、单次响应必须在几十微秒内；以及改派链本身就是要给调度员看的解释，“T5 来了，V5 转去做它，T2 改给 V2，T3 改给 V1”。已经出发的车、已经开始的任务要先从问题里拿掉，只对还没执行的部分重算。
